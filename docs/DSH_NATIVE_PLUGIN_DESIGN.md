## 3. Actual DSH 0.2.0-rc.2 Plugin API

**CONFIRMED:** This is a Cordis plugin, not a single default-export `dsh` plugin object. The first-party `dsh-tool-todo/lib/index.js` exports named `name`, `inject`, `Config`, `apply`; `apply(ctx, config)` registers with `ctx.tools.register(defineTool({...}))`. `inject = ['tools']` expresses the service dependency. Cordis also accepts function/object plugin shapes (`dsh-cordis-host-runner/lib/types/guard.d.ts`); the named-export shape is the recommended local package pattern.

**CONFIRMED:** `defineTool<const S extends ParameterSchemaSpec, const O extends ValueSchemaSpec>(options: DefineToolOptions<S,O>): ToolDefinition` from `@deepseek-ai/dsh-tools` (`schema.d.ts`). Required options: unique `name`, `description`, `parameters`, `output: {schema, render, presentationMeta?}`, `execute(args, exec)`. Optional options include `deferLoading`, `timeoutMs`, `isConcurrencySafe`, `projectContent`, `finalizeContent`, `presentCall`, `presentResult`. `execute` returns a Promise of the schema's canonical JSON value, and `output.render` maps validated value to model-visible `ContentBlock[]`. Output schema is **mandatory**, not merely a TypeScript annotation. Invalid arguments are validated by `defineTool` before execution (`ToolArgsError`).

**CONFIRMED:** The author-facing schema is DSH's `ParameterSchemaSpec`/`ValueSchemaSpec` DSL, compiled to supported JSON Schema; it is not Zod. Root parameters form an implicit open object with per-property `required: true`. Nested objects need explicit `additionalProperties: true|false`; arrays use `items`; optional fields omit `required`; scalar `enum`/`const`, `oneOf` unions, and `json` are supported. The DSL types show string/number/integer/boolean/null/object/array. Its limited vocabulary lacks numeric minimum/maximum in these declarations, so validate engineering ranges in the Python core and/or explicit tool logic. Cordis plugin **configuration** may use Schemastery `Config`, a distinct schema system (`dsh-tool-todo` example).

**CONFIRMED:** `ToolRunContext` (`dsh-tools/lib/types/index.d.ts`) contains call identity, root/parent identity, name, arguments, optional agent, `signal`, plus `deferContext()` and `concludeTurn()`. It does **not** itself expose `subprocess`; the Cordis `ctx` captured by `apply` can expose it if the plugin declares/inherits `subprocess` injection. `ctx.tools.register` returns a disposer and Cordis manages plugin lifecycle. `tools/pre-execute`, `tools/execute`, `tools/post-execute`, `tools/result`, and `tools/change` are event hooks in the same typings. Tool and workflow trace policy should observe these events, without logging secrets or full user input by default.

**CONFIRMED:** Tool names are registry keys. Duplicate names in one layer throw; `run_code` is reserved (`dsh-tools/lib/index.js`, near `register`). No automatic namespace is indicated. Use project-specific names such as `mechanical_calculate_transmitted_torque` if collision risk warrants it, and test the effective profile. The model receives the result of `output.render` in Native mode; PTC `run_code` receives canonical JSON values for nested tool calls (`dsh-tools/lib/index.js` documentation). Distinguish those two presentations in acceptance tests.

**CONFIRMED:** An exception from `execute` yields a tool failure result through the registry. Returned values that violate `output.schema` also fail the tool. The exact model-facing error text and UI presentation for every category are **UNKNOWN** without a live session test; do not use English error text as the machine contract. Use a canonical discriminated JSON success/failure envelope for expected, classified engineering/configuration outcomes; reserve throws for unexpected programming errors and provider failures, then normalize them in the tool boundary where possible. Ensure `output.render` includes the category and safe message for failed envelopes.

## 6. Node/TypeScript ↔ Python Bridge Comparison

| Option | Benefits | Costs / risks | Phase 12B verdict |
|---|---|---|---|
| A. One-shot Python, JSON stdin/stdout | Simple isolated request, deterministic protocol, easy tests, no state leakage; works with direct `python.exe` on Windows | Interpreter startup per call; strict stdout parsing and timeout needed | **Recommend**, through DSH subprocess service |
| B. Persistent stdio worker (NDJSON/JSON-RPC) | Lower startup cost, future batch work | Framing, restart, leaked state, multiplexing, shutdown and recovery complexity | Defer until measured need |
| C. localhost HTTP | Language-neutral, inspectable service | Port/auth/lifecycle/secret exposure, deployment and version drift | Defer; only consider for future CAD/CAE service boundary |
| D. DSH `ctx.subprocess` | Managed process range, argv and stdin, bounded capture, cancellation, credential scrub | Requires injection/provider availability; caller must own deadline, JSON framing and classification | **Use as execution seam for A** |

**CONFIRMED:** `SubprocessRuntime.resolveExecutable(command, env?, signal?)` checks absolute paths or PATH names and rejects relative paths with separators. `spawn({argv, cwd, stdio, graceMs, signal?, env?})` never shell-interprets argv. `stdin: {data: json}` writes and closes; stdout/stderr collect modes take `maxBytes` with optional capped spill. The handle exposes `done` with `exitCode` and signal, collected stream readers, `terminate()`, `waitForExit()`. Timeout classification belongs to the caller; abort starts provider termination. Default environment is scrubbed of credential-shaped names and `DSH_*`; explicit `env` entries override the scrub (`dsh-subprocess/lib/types/{index,types}.d.ts`). For this narrow tool, cap stdout so truncation is a contract failure; never recover huge engineering JSON from a spill file. Cap stderr separately as diagnostic tail. Explicitly test process-range quiescence on Windows.

## 7. Recommended Architecture

Model → typed DSH Tool → one-shot JSON bridge → thin Python engineering adapter → existing calculator → existing Reviewer → existing registry resolver → versioned JSON envelope → DSH output schema/render. For supported chains, the adapter calls existing `run_verified_shaft_strength_chain` with original Python mappings. Do not copy a formula, Reviewer check, handoff transfer, model card, or registry into TypeScript or the adapter. V1.5 remains an adapter layer.

The current torque CLI accepts flags and emits raw JSON. Reviewer CLI reads one JSON stdin and returns PASS/FAIL JSON with codes 0/1/2. Workflow CLI reads exactly two nonempty JSON lines and returns status JSON with codes 0/1/2. Registry CLI accepts `--model-id`. Reusing these CLIs would need multiple Python starts and brittle stderr/code mapping. **Recommend a thin machine adapter entrypoint in Phase 12B** that imports these existing Python APIs, accepts one typed envelope, emits exactly one JSON envelope, and maps categories. It may serialize existing dataclasses and invoke functions; it may not implement engineering mathematics or new Reviewer/lineage/provenance semantics. Keep direct CLIs as independent verification oracles.

## 8. Tool Exposure Policy

Expose task-level verified operations, never arbitrary Python/module/command/path and never raw calculator-only success. The first tool may retain a user-friendly `calculate_transmitted_torque` name, but its successful output must be reviewed and provenance-resolved. If the existing DSH profile exposes Shell too, this Tool cannot stop a model from executing raw CLI commands through Shell; a deployment claiming enforcement must restrict the model's available capabilities and test its effective tool set. The tool itself provides the gate; global bypass prevention also depends on profile capability policy.

## 9. Reviewer Enforcement

Option A (separate calculator and Reviewer Tools) makes the trace visibly show two calls and permits standalone reuse, but the model can stop after the calculator, misroute the JSON, or ignore FAIL. Prompt wording is an insufficient gate. Option B (verified Tool) runs calculator → Reviewer → provenance internally and releases validated success only on PASS. This reduces model-visible granularity but produces a single auditable call with internal phase events. **Choose B.** Keep Reviewer unchanged. Include review status, version, and check summary in the canonical result; on FAIL return `ok:false`, `REVIEW_FAIL`, with no validated result field. Trace each internal phase with call correlation while avoiding full payload logs.

## 10. Verified Handoff Enforcement

Option A exposes torque, statics and combined tools and asks the model to retype T/M; this makes exact lineage unenforceable and creates tampering/rounding risk, despite granular traces and composability. Option B exposes a high-level `analyze_verified_shaft_strength` Tool that internally obtains raw upstream calculator mappings and calls the existing verified workflow. **Choose B for this supported chain.** Its result can include the workflow's source-field names, upstream review statuses and model IDs for debugging and explanation. It limits ad hoc composition to the documented chain, which is appropriate for current scope. Never let model-facing input contain the intermediate `torque_nm` or `max_bending_moment_nm` for this workflow. Do not alter existing workflow semantics.

## 11. Python Interpreter Resolution

Proposed priority: (1) explicit plugin config absolute executable, (2) dedicated `MECHANICAL_AGENT_PYTHON` environment variable, (3) activated `VIRTUAL_ENV` or `CONDA_PREFIX` executable, (4) repository-known opt-in config, (5) bare `python` on scrubbed PATH. Resolve each candidate once and **probe before any engineering call**. Explicit candidates fail closed; do not silently fall through. For auto candidates, record rejected candidates and select only one passing the probe, or return `PYTHON_RESOLUTION_ERROR` with safe diagnostic. Probe Python `>=3.12`, import `mechanical_agent`, inspect installed/project version `0.1.0`, and verify module source is in the intended repository checkout and registry is reachable. Future releases should make expected version configurable or locked to the plugin contract. The historical `C:\Users\ljt\anaconda3\envs\mech-agent\python.exe` is an example, never a source default. Prefer direct env `python.exe` to `conda run` for predictable argv, exit code, startup, cancellation and stdout purity. Do not allow Tool arguments to choose an executable. Pass executable and argv as separate strings; no manual Windows quoting or shell.

## 12. JSON Contract

Proposed adapter request: `{ "contract_version":"1", "operation":"transmitted_torque_v1", "input":{"power_kw":5.5,"speed_rpm":960} }`. The operation is redundant for a single Tool but useful at the shared Python adapter boundary and must be a fixed allowlist, never an arbitrary module/function name. Use UTF-8, exactly one JSON object on stdin and stdout, reject NaN/infinity, unknown versions/operations/fields, and cap bytes. Numeric inputs must be JSON numbers, not bools or free-form unit strings. Tool schema performs shape validation; Python repeats authoritative validation.

Proposed success: `{ "contract_version":"1", "ok":true, "operation":"transmitted_torque_v1", "model_id":"transmitted_torque_v1", "calculator_result":{...}, "review":{"status":"PASS","reviewer_version":"engineering_reviewer_v1","checks":[...]}, "provenance":{"model":{...},"sources":[...]}, "lineage":null, "warnings":[], "metadata":{"python_project_version":"0.1.0"} }`. For a chain, include workflow ID and its existing lineage/status fields. Preserve calculator JSON numbers exactly as Python serialized them; do not recompute or round in TS.

Proposed failure: `{ "contract_version":"1", "ok":false, "operation":"...", "error":{"code":"REVIEW_FAIL","message":"...","details":{}}, "metadata":{} }`. Closed code set: `INVALID_TOOL_INPUT`, `PYTHON_RESOLUTION_ERROR`, `PYTHON_PROCESS_ERROR`, `ENGINEERING_INPUT_ERROR`, `CALCULATOR_ERROR`, `REVIEW_FAIL`, `PROVENANCE_ERROR`, `LINEAGE_ERROR`, `INTERNAL_ADAPTER_ERROR`, `TIMEOUT`, `CANCELLED`. Never include a successful engineering result in a failure envelope. The DSH output schema should use `oneOf` for success/failure and `additionalProperties:false` at critical nesting. Version contract independently of project version.

## 13. Error Semantics

Engineering rejection (`REVIEW_FAIL`, `LINEAGE_ERROR`) is a normally executed Tool returning structured `ok:false`; stop the workflow. User input/schema/range errors return `INVALID_TOOL_INPUT` or `ENGINEERING_INPUT_ERROR`; the model can ask for corrected inputs, with no calculation claims. Wrong interpreter/import/version/spawn/timeout/cancellation is configuration or infrastructure failure and stops all engineering operations. Unexpected malformed adapter stdout or wrong output schema is `INTERNAL_ADAPTER_ERROR` and stops. Unexpected code bugs may throw; the boundary should normalize known spawn/provider exceptions into a safe category and let the registry mark genuinely unexpected throws as failed. The model and user should see category plus concise actionable message, not raw stderr, traceback, secret env or unvalidated numbers. Reviewer CLI codes 0/1/2 remain its own contract; the adapter maps status and payload, never merely the code or a parsed stderr phrase.

## 14. Security Model

Use `ctx.subprocess.spawn` with fixed resolved Python executable, fixed `-m mechanical_agent...` argv and JSON stdin; no `shell:true`, PowerShell string construction or user-supplied module/path/env. Resolve repository root once from trusted plugin config or installation metadata; canonicalize and validate it. Support Windows spaces and UNC via path APIs; reject ambiguous relative executable paths. Inherit only the subprocess service's scrubbed ambient base, then add a small allowlist if genuinely needed; never forward arbitrary Tool input to `env`. Set `cwd` explicitly to the repository root. Bound time, stdout/stderr bytes, input bytes and process termination; classify truncation as a failure. Keep stdout JSON-only; stderr is capped diagnostic data. Forward `exec.signal`, own timeout via an AbortController, await child quiescence. A Cordis VM sandbox for dynamic packages is documented as cooperative, not containment (`dsh-cordis-host-runner/lib/types/sandbox.d.ts`); treat locally loaded plugin code as trusted code.

Never publish merely to test local loading.
